# Диагностика чата Night 0.15

Видео синхронизируется через HTTP API, чат и звук — по WebRTC. Исправная синхронизация видео не подтверждает доступность ICE/STUN/TURN или DataChannel.

## Клиент: night-chat-client.js

Выполни на обоих ПК, пока оба участника находятся в одной комнате и нажали «Подключить чат». Желательно начать диагностику в течение 30 секунд после попытки соединения: сервер хранит сигналинг только 60 секунд.

1. Открой в Night именно страницу комнаты `https://browser.night-watchers.com/room`, обычное окно.
2. Открой файл night-chat-client.js в текстовом редакторе и скопируй его содержимое.
3. Нажми Ctrl+Shift+K — консоль этой страницы. Вставь скрипт и выполни Enter. Глобальная Browser Console не нужна.
4. Подожди примерно 15–30 секунд. Скачается night-chat-client-<время>.json. Если скачивание заблокировано, результат также выведен в консоль и доступен как `window.nightChatDiagnosticReport`.

Скрипт не включает микрофон, не создаёт комнату, не отправляет сообщения и не меняет текущие peer-соединения. Он читает состояние через существующий Night bridge, снимает встроенные сведения RTC и создаёт отдельные временные DataChannel/ICE-пробы. Они закрываются после проверки. Запрашиваются STUN/TURN-серверы из текущей конфигурации; TURN-проба создаёт кратковременную allocation, без аудио.

В отчёте нет Bearer-ключа, TURN-пароля, полного SDP, имени профиля, ссылки на видео или сырых адресов кандидатов. Участники обозначены member-1/member-2 по стабильному порядку ID внутри комнаты. Ошибки/время, типы кандидатов, ICE URL сервера и признаки версии текущего HTTP room.js остаются для сравнения.

Нулевой список сигналов сам по себе не доказывает поломку: записи истекают. Relay-кандидат подтверждает allocation с этого ПК, но не доставку пакетов между обоими участниками. Ошибка ICE 701 может относиться к одному адресу/семейству IP и не означает полный отказ, если другие кандидаты получены. Поздний кандидат после 6 секунд выделен отдельно, потому что текущий room.js отправляет снимок SDP с таким таймаутом.

## Сервер: night-chat-server.py

Запускай от noon, с тем же Docker context, где работает сервис. Нужен Python 3, дополнительных пакетов нет.

```sh
python3 night-chat-server.py
```

По умолчанию: `/home/noon/night-together/services/together`, `https://browser.night-watchers.com`, IP `144.91.104.48`. Создаётся `night-chat-server-report.json` в текущем каталоге. Другие параметры:

```sh
python3 night-chat-server.py --path /home/noon/night-together/services/together --origin https://browser.night-watchers.com --public-ip 144.91.104.48 --output night-chat-server-report.json
```

Скрипт только читает Docker inspect, выбранные файлы и логи, проверяет HTTP и локальный UDP STUN. Он не выполняет sudo, compose up/down, рестарты, регистрацию аккаунтов или изменение firewall/Cloudflare/nginx. Полный Docker inspect, сырые логи, state.json и секреты в отчёт не записываются. Секреты сравниваются внутри процесса; выводится только совпадают ли значения в backend, TURN и сгенерированном turn.conf. Локальная STUN-проверка не доказывает доступность UDP с интернета.

Для разбора нужны два клиентских JSON и один серверный. Если клиентский скрипт не запускается, полезен точный текст ошибки консоли; если bridge доступен, ошибка включена в JSON.

## Проверка самих скриптов

Клиент проверен в двух настоящих процессах Gecko на локальной комнате: читаются состояние/сигналы, действующий DataChannel и ICE-кандидаты, продолжается обмен сообщениями и RTP. Для диагностики микрофон не включается. Серверный сборщик проверен на контролируемых Docker inspect/turn.conf/log fixtures: совпадение и несовпадение секретов распознаются, значения секретов и сырые логи не сериализуются. Это не проверка реальных сетей пользователей или firewall VPS.
